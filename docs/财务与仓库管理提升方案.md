# 财务管理与仓库管理提升方案

> 编制时间：2026-07-09  
> 项目：e-Hfnew（养老企业管理系统）  
> 基于：项目认识文档 + 四轮代码审查报告 + 仓库整改清单20项完成状态

---

## 一、提升目标与原则

### 1.1 总体目标

在现有功能框架基础上，将财务管理与仓库管理从"**功能齐全、数据可录**"提升到"**流程闭环、数据可信、决策可用**"的水平，满足养老机构日常运营和民政局审计合规双要求。

### 1.2 提升原则

1. **合规优先**：五保集中供养资金监管是红线，任何改动不能削弱现有双轨制
2. **闭环驱动**：优先打通断链（采购全流程、预算联动），而非堆叠新功能
3. **数据可信**：解决数据不一致问题（预算执行率、供应类别统计），让报表可被信任
4. **渐进实施**：按 P0→P1→P2 优先级分阶段，每阶段独立交付可验证成果

## 二、财务管理提升方案

### 2.1 阶段一：合规底线与数据可信（P0优先级，1-2周）

#### F-01. ExpenseRecord增加supplyCategory字段

**问题**：当前 `t_expense_record` 缺少 `supply_category` 字段，导致：
- 财务报表无法区分社会化 vs 集中供养支出
- 仓库-财务联动的支出记录无法关联供应类别
- 五保资金使用明细报表数据不完整

**方案**：

```sql
-- 1. 数据库迁移
ALTER TABLE t_expense_record ADD COLUMN supply_category VARCHAR(20) 
  DEFAULT 'CENTRALIZED' COMMENT '供应类别: SOCIAL/CENTRALIZED';

-- 2. 入库同步支出时携带supplyCategory
-- InventoryInService.syncExpense() 方法修改：
--   从 inventoryIn.getSupplyCategory() 取值传入 ExpenseRecord
```

**前端改动**：支出登记表单增加"供应类别"下拉（仅仓库关联支出必填，其余支出可选）

**预估工时**：2h（后端）+ 1h（前端）+ 0.5h（SQL）

#### F-02. JWT密钥环境变量化

**问题**：`application.yml` 中 JWT 密钥为占位字符串，任何拿到配置文件的人可伪造Token

**方案**：

```yaml
# application.yml
access-secret: ${APP_JWT_ACCESS_SECRET:CHANGE_ME_FOR_DEV_ONLY}
refresh-secret: ${APP_JWT_REFRESH_SECRET:CHANGE_ME_FOR_DEV_ONLY}
```

部署脚本中生成随机密钥：
```bash
export APP_JWT_ACCESS_SECRET=$(openssl rand -base64 48)
export APP_JWT_REFRESH_SECRET=$(openssl rand -base64 48)
```

**预估工时**：0.5h

### 2.2 阶段二：流程闭环与预算联动（P1优先级，2-4周）

#### F-05. 预算usedAmount实时联动

**问题**：`t_budget` 表有 `used_amount` 字段但入库时不更新，导致预算执行率数据不准

**方案**：

在 `InventoryInService.create()` 和 `update()` 中增加预算联动逻辑：

```java
// InventoryInService 新增方法
private void syncBudgetUsage(InventoryIn inventoryIn) {
    if (inventoryIn.getSupplyCategory() == SupplyCategory.CENTRALIZED 
        && inventoryIn.getTotalAmount() != null) {
        // 查找当月对应supplyCategory的预算记录
        Budget budget = budgetMapper.findByYearMonthAndCategory(
            inventoryIn.getInDate().getYear(),
            inventoryIn.getInDate().getMonthValue(),
            inventoryIn.getSupplyCategory()
        );
        if (budget != null) {
            budget.setUsedAmount(budget.getUsedAmount() + inventoryIn.getTotalAmount());
            budgetMapper.updateById(budget);
        }
    }
}
```

同理，入库 `update/delete` 时需做差额调整。

**预警联动**：预算使用率 > 80% 时自动触发 `WarehouseAlerts` 中的 `BUDGET_OVERSPENDING` 预警。

**预估工时**：3h（后端）+ 1h（前端展示）

## 三、仓库管理提升方案

### 3.1 阶段一：采购全流程串联（P1优先级，2-3周）

#### W-01. 采购→验收→入库端到端串联

**问题**：四张表（purchase_request / purchase_receipt / inventory_in / expense_record）已存在，但流程未端到端打通

**方案**：

**步骤1：采购申请审批通过后 → 自动生成待验收记录**

```java
// PurchaseRequestService.approve() 方法增加：
public void approve(Long id, Long approverId) {
    PurchaseRequest request = ...;
    request.setApprovalStatus(ApprovalStatus.APPROVED);
    request.setApproverId(approverId);
    request.setApprovalDate(LocalDate.now());
    
    // 新增：自动创建待验收记录
    PurchaseReceipt receipt = new PurchaseReceipt();
    receipt.setPurchaseRequestId(id);
    receipt.setReceiptDate(null); // 待验收
    receipt.setStatus("PENDING");
    purchaseReceiptMapper.insert(receipt);
    
    purchaseRequestMapper.updateById(request);
}
```

**步骤2：到货验收通过后 → 入库表单自动填充采购单数据**

前端 `InventoryIn.vue` 在选择 `inMode=FROM_PURCHASE` 时：
- 从已审批+已验收的采购单自动拉取物资清单（itemsJson解析）
- 自动填充 materialId、quantity、unitPrice、supplier、supplyCategory
- 自动关联 allocationId（从采购单继承）
- 自动关联 purchaseReceiptId

**步骤3：入库完成 → 同步支出记录 → 联动预算usedAmount**

串联链路完成：
```
采购申请(PENDING) → 审批(APPROVED) → 待验收(PENDING) → 验收(PASS) 
    → 入库(FROM_PURCHASE) → 支出记录(supplyCategory) → 预算usedAmount更新
```

**预估工时**：6h（后端串联逻辑）+ 4h（前端交互改造）

#### W-02. StockService支持supplyCategory筛选

**问题**：前端库存看板传了supplyCategory参数，但后端StockService忽略

#### W-03. 出库审批通过 → 自动扣减库存（确保一致性）

**问题**：当前 `OutboundRequestService.approve()` 创建出库记录，但需确认库存扣减逻辑是否在事务内

**方案**：

确保 `approve()` 方法在同一事务中：
1. 创建 `InventoryOut` 记录
2. 调用 `StockService.decreaseStock()` 扣减库存
3. 更新 `OutboundRequest.inventoryOutId`

如果任何步骤失败，整个事务回滚，防止"审批通过但库存没扣"的数据不一致。

**预估工时**：1h（事务边界确认与修复）

## 四、财务-仓库联动提升方案

### 4.1 联动闭环全景

当前联动存在三个断点，修复后形成完整闭环：

```
断点1: ExpenseRecord缺supplyCategory → 修复后: 财务报表可按类别统计
断点2: 采购→验收→入库未串联 → 修复后: 五保资金全链路可追溯
断点3: Budget.usedAmount未联动 → 修复后: 预算执行率实时准确
```

### 4.2 联动数据流（修复后）

```
五保拨付(t_wubao_allocation)
    │
    ↓ allocationId
采购申请(t_purchase_request) ─── 审批 ─── 验收(t_purchase_receipt)
    │                                              │
    ↓ purchaseReceiptId                             ↓
入库(t_inventory_in) ─── supplyCategory ───→ 支出记录(t_expense_record)
    │                                              │
    ↓ 更新库存                                      ↓ 更新预算usedAmount
库存(t_stock)                                   预算(t_budget)
    │                                              │
    ↓ 扣减                                         ↓ 执行率
出库(t_inventory_out) ───→ 仓库成本汇总 ───→ 财务收支对账
    │                                              │
    ↓ 领用老人                                      ↓
消耗趋势分析                                    资金流向报表
```

### 4.3 联动对账增强

#### L-01. 五保资金全链路对账报表

**新增功能**：

一张报表串联五保资金全生命周期：
```
拨款金额 → 已采购金额 → 已入库金额 → 已领用金额 → 剩余可用
  ↓            ↓            ↓            ↓
拨付记录    采购申请    入库记录    出库记录(含受益老人)
```

每个环节可穿透查看明细，满足民政局审计要求。

**预估工时**：6h（后端穿透查询）+ 4h（前端报表页面）

---

#### L-02. 月度财务-仓库对账自动校验

**新增功能**：

月末自动校验以下一致性：
- 入库总金额 = 支出记录中仓库类别总金额（差异 ±0.01 报警）
- CENTRALIZED入库金额 ≤ 当月五保拨付可用余额
- 预算usedAmount = 入库总金额（CENTRALIZED类）
- 银行流水支出合计 = 支出记录合计（按bankAccountId分组）

校验结果生成"对账差异报告"，差异项需人工确认。

**预估工时**：4h（后端校验逻辑）+ 2h（前端报告页面）

## 六、风险与约束

| 风险 | 影响 | 对策 |
|------|------|------|
| 生产安全评分低(4/10) | 上线前必须解决 | 阶段一优先完成F-02/F-03/F-04 |
