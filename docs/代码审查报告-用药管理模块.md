## 三、发现问题

### P1 🟡 功能性问题

#### #1 MedicationPlan.vue — 姓名筛选不生效
**文件**: `frontend/src/pages/pharmacy/MedicationPlan.vue` 第 586 行
**问题**: 前端筛选器 `filterElderly` 发送参数 `elderlyName`，但后端 `listPlans` 只接受 `elderlyId` (Long)。用户输入老人姓名过滤，实际查询被忽略。
```javascript
// 前端发送:
params: { elderlyName: filterElderly.value || undefined }

// 后端接收:
@RequestParam(required = false) Long elderlyId  // ← 不匹配!
```
**建议**: 前端改为调用 elderly options API 做本地匹配，或后端增加 elderlyName 模糊搜索参数。

#### #2 MedicationDashboard.vue — 批量确认无执行人信息
**文件**: `frontend/src/pages/pharmacy/MedicationDashboard.vue` 第 378 行
**问题**: 批量确认只发送 `{ date }`，未传 `executorId/executorName`。后端将 `executorName` 填入字面量 `"批量确认"`，审计记录无法追溯实际操作人。
```javascript
await api.put('/api/medication/records/batch-confirm', { date: selectedDate.value })
// ☝ 缺少 executorId, executorName
```
**建议**: 参考 `submitConfirm()` 的模式，批量确认前弹出护工选择框。

#### #3 MedicationScheduleService — 每日记录生成无去重保护
**文件**: `backend/.../service/MedicationScheduleService.java` 第 42-125 行
**问题**: `generateDailyRecords()` 直接 INSERT 当天记录，若 Spring Boot 重启恰好在 00:01 触发 cron 二次执行，或手动触发，会产生重复记录。缺唯一约束或存在性检查。
```java
// 当前流程: 直接 insert
recordMapper.insert(record);
// 缺少: 检查当天该 plan+slot+drug 是否已有记录
```
**建议**: 插入前用 `LambdaQueryWrapper` 检查 `planId + drugId + recordDate + timeSlot` 唯一性。

#### #4 MedicationService.updatePlan() — 更新后不重新生成记录
**文件**: `backend/.../service/MedicationService.java` 第 114-178 行
**问题**: `createPlan()` 调用 `backfillRecords()` 补充历史记录，但 `updatePlan()` 不调用。用户修改 startDate、timeSlots 或药品清单后，已生成的旧记录与新配置不匹配，也不会生成新日期的记录。
```java
// createPlan 末尾: backfillRecords(plan);  ← 有
// updatePlan 末尾: 无任何记录处理        ← 缺失!
```
**建议**: `updatePlan` 后清理旧日期的 `PENDING` 记录并调用 `backfillRecords()` 重新生成。

#### #5 MedicationService.deletePlan() — 已确认记录被静默删除
**文件**: `backend/.../service/MedicationService.java` 第 196-212 行
**问题**: `deletePlan()` 级联删除所有子记录（含已确认 DONE 记录），审计追溯链断裂。前端删除确认框显示"不可恢复"但未提示有多少条已确认记录。
```java
// 第 206-208 行: 无差别删除 ALL records
recordMapper.delete(recordWrapper);
```
**建议**: 删除时先统计 DONE 记录数，在确认框中展示。或改为只删除 PENDING 记录，保留已确认记录。

### P2 🟢 代码质量

#### #6 Dead Code: calculateDepletionDate(MedicationPlan)
**文件**: `backend/.../service/MedicationService.java` 第 630-645 行
**问题**: 方法引用 `plan.getTotalQuantity()` 和 `plan.getDosagePerTime()` 这些旧字段（已迁移到 PlanItem），且全项目无调用。纯死代码。
**建议**: 删除。

#### #7 confirmBatch — N+1 查询问题
**文件**: `backend/.../service/MedicationService.java` 第 383-388 行
**问题**: 循环中逐个 `selectById` + `updateById`，对 performance 不友好但在计划数少时可接受。
```java
for (Long id : recordIds) {
    confirmRecord(id, executorId, executorName);  // 每次 selectById
}
```
**建议**: 使用 `updateBatchById` 或一条 `UPDATE ... WHERE id IN (...)` 批量更新。

#### #8 exportRecords — 硬编码 LIMIT
**文件**: `backend/.../service/MedicationService.java` 第 466 行
**问题**: `wrapper.last("LIMIT 5000")` 与 MyBatis-Plus 分页体系不兼容，混用 raw SQL。若数据超 5000 条则静默截断。
**建议**: 使用 `Page<>(1, 5000)` 或传入参数控制上限。

#### #9 MedicationPlan.vue — "今日待执行"统计不准确
**文件**: `frontend/src/pages/pharmacy/MedicationPlan.vue` 第 374-376 行
**问题**: 统计卡片显示 `parseTimeSlots × itemsCount` 为 ALL active plans 的理论记录数，未按 `startDate ≤ today` 过滤。标签写"今日待执行"但实际是"全量计划理论记录数"。
```javascript
const todayPending = activeItems.reduce((sum, r) => {
    return sum + parseTimeSlots(r.timeSlots).length * (r.items ? r.items.length : 1)
}, 0)
// ☝ 未过滤 startDate > today 的计划
```
**建议**: 只统计 `startDate <= today` 且状态为 ACTIVE 的计划的理论记录数。
