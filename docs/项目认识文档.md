## 一、项目定位与目标

### 1.1 项目定位

e-Hfnew 是一套面向**中小型养老机构**的全流程数字化管理系统，核心设计原则为"**老人为中心、数据驱动运营**"。系统旨在替代养老机构现有的纸质台账与分散电子表格，实现入住、财务、人事、药物、仓库、上门服务等核心业务的统一数字化管理。

### 1.2 核心目标

- 减少护理漏项、财务误差、跨部门信息断层
- 对接民政局集中供养合规报表需求
- 为管理层提供实时运营看板与决策数据支撑

### 1.3 用户角色体系

| 角色 | 核心职责 |
|------|----------|
| 超级管理员 | 全权限控制、系统配置 |
| 机构负责人 | 运营看板、系统参数配置 |
| 财务人员 | 缴费、凭证、报账、月结、五保拨付 |
| 人事专员 | 护工档案、排班、考勤 |
| 护理主管 | 护工考核、护理计划分配 |
| 护工 | 打卡、护理记录录入 |
| 仓库员 | 物资入出库登记、库存盘点 |
| 药剂员 | 药品管理、发药登记 |
| 上门服务专员 | 预约受理、服务记录提交 |

## 二、技术架构

### 2.1 技术栈总览

| 层级 | 技术选型 | 版本 |
|------|----------|------|
| **前端** | Vue 3 + Vite + Element Plus + Pinia + Vue Router + Axios + ECharts | Vue 3.5.12 / Vite 4.5.3 / ECharts 6.0 |
| **后端** | Spring Boot + Java 17 + MyBatis-Plus + Spring Security + JWT | Spring Boot 3.2.5 / MyBatis-Plus 3.5.5 |
| **数据库** | MySQL 8.0（腾讯云CynosDB） + H2（开发环境） | MySQL 8.0 |
| **认证** | JWT双Token（accessToken 15分钟 + refreshToken 14天）+ RBAC | JJWT 0.12.5 |
| **导出** | Apache POI（Excel报表） | 5.2.5 |
| **日志** | AOP切面全量操作日志 | Spring AOP |
| **定时任务** | Spring @Scheduled（月度账单、用药调度等） | 内置调度器 |
| **部署** | Nginx反向代理 + systemd + Docker Compose可选 | — |

### 2.2 架构分层

```
前端层（Vue3 SPA）
    ↓ Axios REST + JWT
Nginx 反向代理（静态资源 + API路由）
    ↓
后端服务层（Spring Boot API + RBAC权限校验）
    ├── 入住/老人服务
    ├── 人事/护工/排班服务
    ├── 财务服务（缴费/凭证/报账/月结/五保拨付）
    ├── 仓库服务（入库/出库/盘点/采购/验收）
    ├── 药物服务（药品/批次/发药/用药计划）
    ├── 上门服务（预约/记录/评估）
    ├── 系统管理（RBAC/机构/配置/日志）
    └── 报表导出服务
    ↓
数据层（MySQL + OSS对象存储）
```

### 2.3 权限模型

- **RBAC**：角色 → 菜单树 → 按钮级权限控制
- **多租户**：org_id 字段贯穿核心业务表，OrgTenantHandler 自动注入
- **超级管理员**：permissions 含 `*`，跳过所有权限检查
- **前端路由守卫**：基于 permissions 字符串集合拦截

### 4.3 计费引擎（核心业务逻辑）

计费引擎位于 `FeeBillService.java`（约29KB），是整个财务模块的核心引擎：

| 规则编号 | 适用场景 | 计费公式 |
|:--------:|----------|----------|
| **规则A** | 短期入住（≤7天） | 日费用 = 180元/天，月应收 = 180 × 实住天数 |
| **规则B** | 正常入住（>7天） | 月应收 = (合同月费 / 当月自然日数) × 实住天数 |
| **规则C** | 月末未住满 | 多收费用顺延至下月冲抵，不退款 |
| **规则D** | 费用预警 | 余额 < 7日费用时触发首页提醒条 |

### 4.4 月账单生命周期

```
生成草稿(DRAFT) → 确认结算(CONFIRMED) → 标记结清(SETTLED)
    POST                PUT                    PUT
 /bills/generate    /bills/{id}/confirm    /bills/{id}/settle
```

- 批量结算：`POST /bills/settle-month` 结算指定月份所有已确认账单
- 补贴汇总：`GET /bills/subsidy-summary` 查看补贴明细

### 4.5 补贴计算逻辑

三种计算模式：

| calcType | 说明 | 示例 |
|----------|------|------|
| FIXED_MONTHLY | 固定月额补贴 | 五保对象每月固定800元 |
| DAILY_RATE | 日补贴率 | 长护险按日计费，与五保去重 |
| THRESHOLD_DEDUCT | 满额抵扣 | 消费券阶梯抵扣 |

请假天数自动关联 `t_elderly_leave` 扣减实住天数。

## 五、仓库管理模块现状

### 5.1 模块定位

仓库管理是系统中**功能改造最剧烈**的模块，经历了从单体库存表到ERP级模块架构的完整升级（20项整改清单全部落地），核心设计特征为**供应类别双轨制**——社会化(SOCIAL)与集中供养(CENTRALIZED)物资完全隔离管理，满足民政局五保资金监管合规要求。

### 5.2 数据模型（12+张核心表）

| 表名 | 功能 | 核心字段 |
|------|------|----------|
| **t_material** | 物资档案 | name, category(5大类), specification, unit, warningThreshold |
| **t_stock** | 库存（双轨） | materialId, supplyCategory(SOCIAL/CENTRALIZED), quantity, totalValue；UNIQUE(materialId, supplyCategory) |
| **t_inventory_in** | 入库记录 | materialId, supplier, quantity, unitPrice, totalAmount, inDate, supplyCategory, allocationId(拨款关联), purchaseReceiptId(验收关联), inMode(DIRECT/FROM_PURCHASE), expenseRecordId(支出关联) |
| **t_inventory_out** | 出库记录 | materialId, department, purpose, quantity, outDate, status(PENDING/APPROVED/REJECTED), supplyCategory, recipientStaffId, recipientName, recipientSignUrl |
| **t_inventory_check** | 盘点记录 | materialId, supplyCategory, systemQuantity, actualQuantity, difference, checkDate |
| **t_inventory_batch** | 批次追踪 | materialId, batchNo, supplyCategory, quantity, remainingQuantity, expiryDate, inDate, inventoryInId |
| **t_supplier** | 供应商主数据 | name, creditCode(统一信用代码), contact, phone, bankName, bankAccount, status |
| **t_purchase_request** | 采购申请 | requestNo, applicantId, itemsJson(JSON), totalAmount, supplyCategory, allocationId, supplierId, approvalStatus(PENDING→APPROVED→REJECTED) |
| **t_purchase_receipt** | 到货验收 | purchaseRequestId, inspectorId, inspectResult(PASS/FAIL), actualQuantity, receiptDate |
| **t_outbound_request** | 出库审批 | applicantId, materialId, quantity, supplyCategory, department, purpose, recipientStaffId, approvalStatus, inventoryOutId |
| **t_budget** | 预算 | year, month, supplyCategory, budgetAmount, usedAmount |

### 5.3 供应类别双轨制（核心设计）

这是仓库管理最重要的架构特征：

- **SOCIAL（社会化物资）**：老人家属自费购买的物资，直接入库/出库
- **CENTRALIZED（集中供养物资）**：民政局五保资金拨付采购的物资，需走完整采购审批流程

**关键机制**：
- 库存按 `(materialId, supplyCategory)` 拆分为两行独立记录
- 出库时跨类别操作会被拦截（抛"库存不足"异常）
- 集中供养物资强制走：采购申请 → 审批 → 验收 → 入库链路
- 社会化物资可保留直接入库/出库模式

### 5.4 仓库业务流程

#### 5.4.1 入库流程（双模式）

```
模式1: 直接入库(DIRECT)
  登记入库 → 同步写库存 + 可选同步支出记录

模式2: 从采购单入库(FROM_PURCHASE)
  采购申请 → 审批 → 到货验收 → 入库 → 同步支出记录 + 关联拨款批次
```

#### 5.4.2 出库流程（审批制）

```
领用申请(OutboundRequest) → 审批(APPROVED) → 自动生成出库记录 → 扣减库存
  集中供养物资必须走审批流程
  社会化物资可直接出库或走审批
```

#### 5.4.3 盘点流程

```
发起盘点 → 记录systemQuantity vs actualQuantity → 计算difference → 库存调整
```

## 七、代码审查与项目成熟度

### 7.1 审查历史

| 轮次 | 重点 | 关键发现 |

### 7.2 正向评价

1. 库存同步逻辑完善（update/delete正确处理差额和跨类别迁移）
2. 审批状态机严谨（PENDING状态校验防重复操作）
3. JWT Token刷新去重（isRefreshing + 共享Promise防并发401）
4. 月度费用补贴计算覆盖完善（五保/长护险去重/消费券阶梯抵扣）
