## 二、正向评价 ✅

1. **库存同步逻辑完善** — `InventoryInService.update/delete` 和 `InventoryOutService.update/delete` 均正确处理了 old→new 的差额计算和跨物资/跨类别迁移（`materialChanged` 分支），扣减前有负库存检查
2. **审批状态机严谨** — `OutboundRequestService` 和 `PurchaseRequestService` 的 approve/reject 均有 `PENDING` 状态校验，防止重复操作
3. **JWT Token 刷新去重** — `client.js` 的 `isRefreshing` + 共享 Promise 模式防止并发 401 时重复刷新
4. **ThreadLocal 清理** — `JwtAuthenticationFilter` 在 `finally` 块中清理 `OrgContextHolder`，无内存泄漏
5. **CORS 配置严谨** — 显式列出 allowed origins，不使用 `*`，且 `allowedHeaders` 也是白名单
6. **月度费用结算逻辑** — `FeeBillService` 的补贴计算覆盖了五保、长护险去重、消费券阶梯抵扣，假期扣减逻辑完善
7. **定时任务错误隔离** — `BillingScheduleService` 和 `MedicationScheduleService` 中每个步骤独立 try/catch，单步失败不影响后续

## 三、发现问题

### 🔴 P0 — 生产环境必须立即修复

#### P0-1. JWT 密钥使用占位字符串
**文件**: `backend/src/main/resources/application.yml:26-27`
```yaml
access-secret: "CHANGE_ME_ACCESS_SECRET_CHANGE_ME_ACCESS_SECRET"
refresh-secret: "CHANGE_ME_REFRESH_SECRET_CHANGE_ME_REFRESH_SECRET"
```
**问题**: 任何拿到配置文件的人都能伪造 JWT Token，突破全部认证。  
**修复**: 通过环境变量注入（`${APP_JWT_ACCESS_SECRET}`），禁止硬编码。部署脚本中生成随机密钥：
```bash
APP_JWT_ACCESS_SECRET=$(openssl rand -base64 48)
```
**影响**: 全系统认证失效 | **预估工时**: 0.5h

---

#### P0-2. 每次启动重新执行 schema.sql
**文件**: `backend/src/main/resources/application.yml:46-49`
```yaml
sql:
  init:
    mode: always              # ← 每一轮启动都执行 DDL
    schema-locations: classpath:schema.sql
    data-locations: classpath:data-mysql.sql
```
**问题**: 生产环境每次重启都会执行 `CREATE TABLE IF NOT EXISTS` 和 `INSERT` 种子数据，轻则报错（表已存在），重则覆盖已有数据。  
**修复**: 
```yaml
sql.init.mode: never  # 生产环境
```
或使用 profile 隔离：
```yaml
# application-mysql.yml (生产)
spring.sql.init.mode: never
# application-h2.yml (开发)
spring.sql.init.mode: always
```
**影响**: 可能覆盖生产数据 | **预估工时**: 0.5h

---

#### P0-3. MyBatis-Plus SQL 日志泄露敏感数据
**文件**: `backend/src/main/resources/application.yml:13`
```yaml
log-impl: org.apache.ibatis.logging.stdout.StdOutImpl
```
**问题**: 生产环境将所有 SQL 语句（含参数）输出到 stdout，包括用户密码、身份证号、金额等敏感信息。日志文件可能被未授权访问。同时造成显著 I/O 性能损耗。  
**修复**: 生产 profile 中覆盖：
```yaml
# application-mysql.yml
mybatis-plus:
  configuration:
    log-impl: org.apache.ibatis.logging.nologging.NoLoggingImpl
```
**影响**: 敏感数据泄露 + 性能损耗 | **预估工时**: 0.25h

---

#### P0-4. 上传文件 >1MB 静默失败
**三层限制未对齐**:

| 层 | 配置项 | 当前值 | 需要值 |
|----|--------|--------|--------|
| Nginx | `client_max_body_size` | 未设置（默认1MB） | 10M |
| Spring | `spring.servlet.multipart.max-file-size` | 未设置（默认1MB） | 10MB |
| App | `FileUploadController.MAX_FILE_SIZE` | 5MB | 保持一致 |

**文件1**: `deploy/nginx.conf` — 在 `server` 块中添加:
```nginx
client_max_body_size 10M;
```

**文件2**: `backend/src/main/resources/application.yml` — 在 `spring:` 下添加:
```yaml
spring:
  servlet:
    multipart:
      max-file-size: 10MB
      max-request-size: 10MB
```
**影响**: 居家评估的上传照片功能（评估表+2签名=通常3-5MB）在生产环境静默失败 | **预估工时**: 0.5h

---

#### P0-5. 上传图片在 Nginx 层面不可访问
**文件**: `deploy/nginx.conf`  
**问题**: nginx.conf 中没有 `/uploads/` 的 location 块。当用户访问 `/uploads/xxx.jpg` 时，nginx 的 SPA fallback (`try_files $uri /index.html`) 会返回 `index.html` 而非图片。图片虽然在 Spring Boot 的 8080 端口可访问，但用户通过 80 端口访问时无法获取。  
**修复**: 在 `location /api/` 之后添加:
```nginx
location /uploads/ {
    proxy_pass http://127.0.0.1:8080;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
}
```
**影响**: 所有已上传的评估照片、签名图片均无法在浏览器显示 | **预估工时**: 0.25h

---

#### P0-6. 前端 `apiBaseUrl` fallback 指向 `localhost:8080`
**文件**: 
- `frontend/src/pages/home-service/Assessment.vue:429`
- `frontend/src/pages/home-service/Records.vue:121`
```javascript
const apiBaseUrl = import.meta.env.VITE_API_BASE_URL || 'http://localhost:8080'
```
**问题**: 生产环境部署时，`VITE_API_BASE_URL` 未设置（应为 `''`），fallback 为 `http://localhost:8080`。`fullUrl()` 函数（Assessment.vue:526, Records.vue:154）将拼接出 `http://localhost:8080/uploads/xxx.jpg`，浏览器无法访问。  
**修复**: 改为：
```javascript
const apiBaseUrl = import.meta.env.VITE_API_BASE_URL || ''
```
同时在 `deploy/frontend.env.example` 中明确生产环境配置：
```env
VITE_API_BASE_URL=
```
**影响**: 同上 P0-5 | **预估工时**: 0.25h

### 🟡 P1 — 生产环境需要尽快处理

#### P1-1. FeeBillController 全部端点缺少 @PreAuthorize
**文件**: `backend/.../controller/FeeBillController.java`  
**状态**: 整个类（6个端点）没有 `@PreAuthorize` 注解  
**影响**: 任何已登录用户都可以生成账单草稿、确认账单、结算扣费。虽然 `SecurityConfig` 要求认证，但缺乏权限粒度控制。月度批量结算可意外触发扣费。  
**修复**: 添加权限注解：
```java
@PreAuthorize("hasAuthority('finance:billing')")  // 查看
@PreAuthorize("hasAuthority('finance:billing:manage')")  // 操作
```
**预估工时**: 0.5h

- `GET /api/finance/cashflow/summary` (line 60) — 无权限

#### P1-4. H2 Console 在所有 profile 均开放
**文件**: `backend/.../security/SecurityConfig.java:50`
```java
.requestMatchers("/h2-console/**").permitAll()
```
**问题**: H2 Console 仅在 h2 profile 下需要。MySQL profile 下虽然端口不会启动 H2 Console，但安全配置中仍然 permitAll。应在仅 h2 profile 时放行。  
**修复**: 使用 `@Profile("h2")` 条件配置，或在 `SecurityConfig` 中检查 active profile。  
**预估工时**: 0.25h

#### P1-5. 生产 Nginx 缺少 HTTPS 和上传超时
**文件**: `deploy/nginx.conf`  
**缺失项**:
1. 无 SSL/HTTPS 配置 — 密码和 JWT 明码传输
2. `location /api/` 没有 `proxy_read_timeout` — 大文件上传可能超时
3. 缺少安全头: `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`（除了 h2-console）

**修复**:
```nginx
server {
    listen 443 ssl;
    # ... SSL cert config ...
}

# API location block:
location /api/ {
    proxy_read_timeout 300s;
    # ...
}

# Security headers:
add_header X-Content-Type-Options "nosniff" always;
```
**预估工时**: 1h（含 SSL 证书配置）

#### P1-6. ExpenseRecord.update() 不追溯银行流水
**文件**: `backend/.../service/ExpenseRecordService.java:102-127`  
**问题**: `create()` 会调用 `bankAccountService.recordExpenseTransaction()` 记录流水，但 `update()` 修改金额后不更新/冲销银行流水，导致流水与实际支出不一致。  
**修复**: `update()` 中也调 `bankAccountService` 更新对应流水记录。  
**预估工时**: 0.5h
